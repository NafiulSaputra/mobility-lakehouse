# 0013. Benchmark methodology

- Status: Accepted
- Date: 2026-10-08
- Decider: Nafiul Hadi Saputra

## Context

Version 1.0 should say how fast the pipeline is, locally and on Databricks, and how fast the stream
processes events. A single timing is easy to produce and easy to misread: the first Spark job of a session
pays for JVM warm-up, serverless compute pays for start-up, and a laptop is busy with other work.

## Decision

- **Local:** `mobility-lakehouse benchmark --month 2025-01 --repeats 3` runs bronze, silver, gold and the
  API snapshot three times in one Spark session inside Docker. Each step replaces the month, so every repeat
  does the full work. The report gives the median, minimum and maximum per step and for the four steps
  together, every single timing, the rows processed and the environment (CPU cores, driver memory, Spark
  and Python versions).
- **Databricks:** timings come from the job run history, not from a stopwatch. `databricks jobs list-runs`
  writes the runs as JSON; `mobility-lakehouse databricks-timings` keeps the successful ones and reports
  the median, minimum and maximum per task and for the whole job. Task times include serverless start-up,
  because that is what a scheduled job pays.
- **Streaming:** events per second over the recorded `--until-caught-up` runs (Sprint 8 run log), Spark
  start-up included.
- **Reports are committed** under `docs/benchmarks`, generated by the commands above, never edited by hand.
- **No cross-platform ranking.** Local and Databricks numbers are reported side by side, not as "faster" or
  "slower": the hardware, the start-up costs and the storage differ.

## Consequences

- Anyone can rerun the same commands and compare their numbers with the committed reports.
- Medians of three runs reduce the effect of one slow run, but three runs are not a statistical study. The
  reports show every run, so the spread is visible.
- Databricks Free Edition timings depend on shared serverless capacity and can change from day to day.

## Alternatives considered

- **One timed run per step.** Simple, but mixes warm-up with the real cost. Rejected.
- **A separate Spark session per repeat.** Measures cold starts every time, which hides the cost of the work
  itself. Rejected; the first repeat already shows the cold cost.
- **Timing Databricks runs by hand from the UI.** Not repeatable and easy to mistype. Rejected.
